# 官方数据接入设计：从「手工坐标」到「多源坐标库」

> 结论先行：官方大地图的数据**能用**，但必须先解出一个**每张图各自的镜像相似变换**。
> 目前已解出清河、开封两图（相对误差 2.2% / 2.1%），官方 3247 个点已进流水线。
> 剩下 7 张图缺锚点，**需要明天进游戏抄 5~6 个界碑坐标**，每张图 3 分钟。

| 传送点 | 18 个（有名字） | **289 个** |
| 宝箱 | 1284 | **4338** |
| 区域覆盖 | 只有清河 / 开封 | 9 张图（河西 / 江南 / 青州…） |
| 描述信息 | 部分有 | **几乎每个点都有「怎么拿」** |

**所以设计目标不是「用官方替换手工」，而是两源并存、各取所长。**

## 2. 关键发现：官方经纬度是什么

### 2.1 不是全球地理坐标，而是「每图各自的画布坐标」

官方接口 `GET /category/points?mapId=<n>` 返回每张图各自的 `longitude/latitude`。
每张图的包围盒是**彼此独立的一块区域**，不是拼起来的连续世界地图：

```
map0 清河     lng [-362172,    -41436]   lat [  54222,  343634]
map1 开封     lng [-425207,    111546]   lat [-152525,  505770]
map2 河西     lng [-1016442,   -57557]   lat [ 122500,  766031]
```

决定性证据 —— 用各自参数投影到我方坐标系后，两片**并集恰好落在我方数据范围内**：

```
map0 投影 -> x[-4058, -1877]  y[-2544,   -84]
map1 投影 -> x[-2895,   461]  y[-1149,  1590]
并集        x[-4058,   461]  y[-2544,  1590]
我方实际    x[-4066,   472]  y[-2597,  1515]     ← 吻合
```

更直接的证据是缩放比：map0 = 0.0076177，map1 = 0.0050777，**比值 1.5002 ≈ 3/2**。
把 map0 的参数套到 map1 上，RMS 从 47 涨到 2485。所以**必须逐图解算**。

> 顺带解释了另一个谜：我们的世界坐标是**连续统一**的（清河 x≈-3000~-4000，开封 x≈-1300~-2700），
> 而官方把它切成了 9 张画布。

### 2.2 变换类型：镜像相似变换（4 参数）

仿射拟合出的线性部分**行列式为负**：

```
map0 affine 线性部分  [[ 0.00000433, -0.00753771],
                      [-0.00766909, -0.00006328]]     det = -5.78e-5  < 0
```

负行列式 = **镜像**。`e1→(0.000004, -0.007669)` 的正交像应是 `e2→(0.007669, 0.000004)`，
实际却是 `(-0.007538, -0.000063)` —— **符号相反**。

这一步卡了很久：两像向量**正交（夹角 89.55°）且等长（比 1.017）**，
看起来完全就是旋转。我当时据此判定「仿射不过是纯旋转」，于是把 similarity 高达
25%/42% 的误差归因于「少数错配点拖垮了最小二乘」，还专门写了 RANSAC 去剔点。
**方向是错的** —— 正交+等长对旋转和镜像都成立，区别在**定向**（det 符号）。
`fit_similarity` 的参数化 `[[a,-b],[b,a]]` 的 det = a²+b² > 0，**永远拟不出镜像**。

正确模型（仍只 4 个参数）：

```
v = -lat                       # 一次镜像
x = a*lng - b*v + tx
y = b*lng + a*v + ty
```

实现上等价于把输入换成 `(lng, -lat)` 再做普通相似变换。

### 2.3 三种模型的诚实对比（LOO 交叉验证）

留一交叉验证是唯一能回答「参数是不是过拟合」的方法 —— 每次拿掉一个点、
用其余点拟合、预测被拿掉的那个点。

| 图 | 模型 | 内点 RMS | **LOO 相对误差** | 结论 |
| --- | --- | --- | --- | --- |
| map0 清河 | similarity（4参·仅旋转） | 689.7 | 25.47% | ✗ 模型族选窄了 |
| map0 清河 | **reflected（4参·可镜像）** | 64.4 | **2.35%** | ✓ **采用** |
| map0 清河 | affine（6参） | 64.1 | 2.40% | 参数更多，没更好 |
| map1 开封 | similarity（4参·仅旋转） | 912.1 | 41.75% | ✗ |
| map1 开封 | **reflected（4参·可镜像）** | 47.1 | **2.14%** | ✓ **采用** |
| map1 开封 | affine（6参） | 46.0 | 2.45% | 参数更多，更差 |

镜像相似变换**全面胜出**：比 6 参数仿射误差更低、参数更少、能外推。
（map1 只有 9 对点，6 参数仿射的 2.45% vs 4 参数的 2.14% 说明自由度高反而在过拟合。）

## 3. 踩过的坑（都留了痕迹在代码注释里）

### 3.1 用「区域地名」当锚点是错的

最早用 20 个同名**地点**拟合：相似 RMS 104738、仿射 RMS 82342（跨度 299820），
RANSAC 最大一致子集只有 4/20。

失败原因不是模型不够，而是**锚点不是对应点**：
官方的区域条目是**标注图钉**，我们数据里的 `place` 字段是**名字含该地名的点云重心**。
两个不同的物理位置，拟合必然崩。

→ 正确做法是**点级匹配**：官方「传送点」里的「佛爷寨」，对应我们数据里的「佛爷寨界碑」。

### 3.2 一个官方点喂了我方两个候选

我方同一实体常有多条记录：「地点标记 / 佛爷寨」与「设施与NPC / 佛爷寨界碑」，
两者相距可达 **137**（慈心山院）。早先允许一个官方点同时对上这两个候选，
几何上自相矛盾，把 map0 的相对误差从 **2.2% 拖到 24.5%**。

→ 一个官方点 → **恰好一个**我方点，优先级：
`设施与NPC`（界碑/传送点，可传送实体）> `地点标记`（地图标签）。

> 物理依据：燕云十六声里**界碑才是可传送实体**，官方「传送点」分类指的是它；
> 「地点标记」是地图上的地名标签，位置是标签锚点，未必落在界碑上。

### 3.3 跨分类的「同名」几乎全是假匹配

官方未命名的点会**退回用分类名当名字**：

```
猫戏      250 点，名字「猫戏」重复 58 次
曲径寻幽   113 点，「曲径寻幽」重复 75 次（66%）
天地万籁    98 点，「天地万籁」重复 63 次（64%）
营地       20 点，「营地」重复 20 次（100%）
```

用这些分类做「独立验证」，得到 31%~91% 的误差 —— 但那是**假匹配**：
我方一个叫「猫戏」的点，被拿去对照官方散落全图的 23 个「猫戏」点。

→ 唯一可靠的锚点分类是**传送点**（289 点里 288 个名字唯一）。
→ 独立验证这条路走不通，所以回到 **LOO 交叉验证**，它是干净可信的。

### 3.4 RANSAC 写错会制造「虚低误差」

第一版 `ransac()` 把 `best` 初始化成**全部点**，而更新条件是 `len(inl) > len(best)`
—— 永远不成立。函数退化成「只用局部精修不断收缩」，
在阈值 1% 时把 38 对点缩到 5 对，然后在这 5 对上算 LOO = 0.92%。

这是典型的**选择偏差**：挑出最自洽的子集，再测量自己的自洽程度。
诚实的数字是全集 LOO = 2.35%。而且全集里**根本没有需要剔除的错配点**
（最大残差 106，仅跨度的 2.2%）。

→ 修好 RANSAC（`best` 初始化为空、精修只允许增长），并把默认改成**不剔除**。

## 4. 流水线里的位置

```
官方接口  s3.game.163.com/ac59075b964b0715/category/points?mapId=<n>
   │
   │  tools/fetch_official.py          拉取 + 本地缓存
   ▼
data/official_points.json              8192 点（含 description）
   │
   │  tools/fit_official_transform.py  逐图解算 + LOO 验证
   │   + data/anchors_manual.json       ← 游戏内实测锚点（map2~8 靠它）
   ▼
data/official_transform.json           每图一组 4 参数 + 可信度
   │
   │  tools/import_official.py         换算 + 写我方原始格式
   ▼
raw/official/<图>/<官方分类>.ini        x ,y ,z ,名称（描述）
   │
   │  tools/etl.py                     和手工数据一起进流水线
   ▼
data/points.json  →  web/public/data  →  WebUI
```

### 为什么写进 `raw/official/` 而不是别处

* `00_import_raw.py --force` 会清空 `raw/`，但**保留 `raw/rpa/` 与 `raw/official/`**
  （它们不是「原始手工坐标库」的副本，清掉就得重新采集/换算）。
* 溯源天然清晰：每个点的 `sources[].file` 会带 `official/`，WebUI 里一眼能认出是官方数据。
* ETL **一行都不用改**。

### description 怎么零改动进 `note` 字段

`lib_parse.split_note` 把**括号收尾**的文字当备注，正则 `[（(]([^）)]*)[)）]$`。
所以把 description 放在名称末尾括号里即可自动拆成 `name` + `note`。

注意正则要求**括号内不含括号** —— description 里的 `（）()` 必须替换掉
（`import_official.py` 里换成 `·`），否则匹配不到。

### 命名规则

| 官方分类 | 处理 | 例 |
| --- | --- | --- |
| 传送点 / 见闻 / 万事知 / 心法 / 奇术 / 野外首领 / 奇遇 / 前尘旧物 / 其他 / 不平事 | **保留原名**（名字唯一） | `佛爷寨`、`【神仙渡·见闻】第一枝花` |
| 宝箱收集 / 蹊跷采集 / 妙妙喵 / 猫戏 / 曲径寻幽 / 天地万籁 / 武学 / 野祀游火 | **编号命名**（占位名重复率 > 40%） | `清河蹊跷采集12` |

判据只用一个：该 (图, 分类) 内最高频名字的占比 > 40%。

> 这里也踩过坑：最初多加了一条 `len(ps) > 50`，
> 结果把**见闻**（521 点里 518 个名字唯一）也编号了，
> 白丢官方最有信息量的那批名字。**只用重复率判断，不要附加「点数多就编号」。**

### 重复覆盖的处理

官方「传送点」110 个点与我们手工的 70 个「XX界碑 / XX传送点」是**同一批实体**。
两份都留会在地图上叠出重影。

→ `import_official.py` 读**上一轮 ETL 输出**，按归一化名称 + 距离 ≤ 400 判定「已被覆盖」，
跳过对应的官方点（本次跳过 76 个）。**保留我方那份** —— 它是在游戏内按坐标读数抄的，
比官方地图上手的图钉更贴近实际可传送位置；而且留两份没有任何额外信息。

参照索引会**排除 `sources[].file` 里带 `official/` 的点**，
否则会拿上一轮导入的官方点去过滤这一轮的官方点，自己把自己清空。

## 6. 明天进游戏要做什么（等锚点）

map2~8 解不出来的原因很直接：**原始手工坐标库只覆盖清河与开封**
（region 分布：开封 3941、清河 2130，其余为空），所以没有对应点可用。

### 采集协议（每张图 3 分钟）

1. 传送到目标区域，找一个**界碑**，走到它旁边；
2. 读游戏内世界坐标 `(x, y)`，记下界碑名字（**必须与官方大地图上的名字一致**）；
3. 每张图记 **5~6 个**，且**尽量分散**（点挤在一起会让 4 参数拟合不稳）；
4. 写进 `data/anchors_manual.json`：

```json
[
  {"name": "界碑名", "x": 1234.5, "y": -678.9, "mapId": 2},
  {"name": "另一个界碑", "x": 2345.6, "y": -789.0, "mapId": 2}
]
```

`lng/lat` 不用抄 —— 脚本会自动用官方同名传送点补齐。若同名候选不唯一，
就显式给出 `"lng"` 与 `"lat"`。

5. 重跑：

```bash
python tools/fit_official_transform.py     # 解算，会打印每图的 LOO 误差
python tools/import_official.py            # 换算进 raw/official/
python tools/etl.py && python tools/verify.py
node tools/sync_web_data.mjs
```

**3 对点就能解出 4 参数**，但 LOO 交叉验证需要 ≥6 对才有意义。
每张图给 6 个分散的界碑，就能得到和 map0 同级的可信度。

### 顺带要验证的事

* **换算精度**：拿一个已解算图的传送点，用识途走过去，对比落点与预期位置。
  2.2% 相对误差 ≈ 60 世界单位，约为相邻界碑间距的 6~10%。若实际偏差明显更大，
  说明官方地图的图钉本身有手放误差，需要把 `--cover-tol` 调整后再评估。
* **识途可用性**：`rpa/navigate.py` 的「开地图 → 选目标 → 点【识途】」流程，
  配合官方点位（数量是手工库的 16 倍）才是真正能用的自动寻路。
* **传送点优先**：优先用官方 `传送点`（289 个）而不是我们的 18 个，
  因为传送到最近的界碑再走，比从远处跑过去快得多。

## 8. 游戏内实测（2026-09-22，游戏 v1.9.69 运行中）

工具链在真实游戏里跑通了，同时推翻了一个原本写在计划里的假设。

### 8.1 链路验证结果

| 项目 | 结果 |
| --- | --- |
| 抓屏（GDI `CreateDIBSection`） | ✓ 42 ms/帧，整屏 881×1600 |
| 灰度 + 模板匹配 | ✓ 自检 score=1.00000，位置精确 |
| **世界模式下发键** | ✓ **按 `m` 帧差 67.62**（地图展开）—— DirectInput 扫描码链路可用 |
| 连续静止检测 | ✓ `MotionDetector.wait_until_still` 正常 |
| 窗口定位 | 游戏 `hwnd=2560354`，客户区 1600×881 @ (0,12) |
| 双显示器 | 虚拟屏 3040×900（主屏 1600×900） |

**发键真的到了游戏里**，这一点不靠「函数返回 True」判断 —— 那只说明 `SendInput` 调用成功。
判据是**画面帧差**：发键前后各抓一帧比差异，显著变化才算到了。

### 8.2 实测抓到的两个真 bug

**① `find_window` 子串匹配被同名第三方工具骗到**

游戏窗口标题是「燕云十六声」，而**律匠的窗口标题是
「律匠 - 燕云十六声装备调律工具 v0.12.2 [只读实例]」—— 同样含这四个字**。
`find_window("燕云十六声")` 返回了律匠的窗口（客户区 1066×700），
后续所有操作都打在律匠上 —— 它不报错、只是没反应，极难排查。

修法：多命中时**优先完全相等**、其次**标题更短**的；
并新增 `find_game_window()`，用**进程名（yysls）+ 标题**双重限定。

**② 没有把窗口调到前台的能力**

`injector.py` 原本没有聚焦函数。Windows 有「前台锁」：
非前台进程调 `SetForegroundWindow` 会**静默失败**（返回 0、不抛异常），
表现就是「脚本以为切过去了，键全打到别的窗口上」。

新增 `focus_window()` / `ensure_foreground()`，三级兜底：
已在前台就返回 → `ShowWindow(SW_RESTORE)` + `SetForegroundWindow` →
还不行就 `AttachThreadInput` 临时挂到前台窗口输入队列（改完立刻解挂）。

### 8.3 关键否定结论：游戏 UI 不显示世界坐标

原始数据精度到小数点后 4 位（`-3022.27, -1225.51, -42.5287`），
本以为是抄游戏里的坐标读数。**实测四个地方都没有**：

| 查看位置 | 结果 |
| --- | --- |
| 世界模式 HUD | 只有 `ID:0367454168` / `0922 08:58` / `44ms` / `FPS 10`，无坐标 |
| 大地图界面 | 只有区域名+探索度（`开封·琼林苑 18%`）、材料列表、`返回R / 标点筛选Q / 材料追踪V / 通知设置T` |
| 地图上悬停 6 个位置 | 左下信息区始终只显示区域名，无坐标变化 |
| 地图上右键 | 只弹出图层 tooltip（`物种分布 / 探索·采集`），无标点菜单 |

**推论**：原始坐标必然来自程序化来源（内存读取或游戏文件），不是屏幕读数。
这意味着 **「进游戏抄界碑坐标来补 map2~8 锚点」这条路走不通** —— 计划里的第 6 节需要改。

同时这也解释了为什么**律匠是纯视觉只读工具**（见 8.4）。

### 8.4 律匠的技术栈与可借鉴之处

查了 `E:\basesoft\tools\律匠\_internal`（PyInstaller 打包）：

```
python312.dll + PyInstaller       Python 3.12
PyQt6                             界面 + 叠加窗口（Border Overlay）
cv2 / numpy / PIL                 图像处理
onnxruntime + rapidocr_onnxruntime← PP-OCRv4 det/rec（OCR）
av (PyAV / ffmpeg)                抓帧
Shapely + pyclipper               几何运算（画边框）
```

**它没有任何内存读取或输入注入库**
（pymem / frida / pywin32 / pydirectinput / keyboard / mouse / uiautomation 全无）。
所以它的「捕捉」= **抓屏 + OpenCV + OCR**，而且它**连发键的能力都没有**，是纯只读工具。

这给了两条明确结论：

1. **选型被旁证**：RapidOCR 在这个游戏的实际画面上验证过可用 —— 这是选型时最有力的证据。
   我们据此给工具箱补了 `rpa/ocr.py`。
2. **我们的能力面更宽**：律匠只有「读」，我们「读 + 写」（扫描码发键）。
   把两者合起来才可能做自动化。

> 许可提示：律匠是 **PolyForm Noncommercial 1.0.0**。
> 这里只借鉴「用 OCR 读屏」这个思路和它对引擎的选择，**不抄它的代码**。

### 8.5 顺带拿到的好处：cv2 让匹配快 6 倍

装 RapidOCR 会顺带装上 `opencv-python`。cv2 一旦可用，
`vision.ncc_map` 就会走 `cv2.matchTemplate` 分支 —— 实测：

```
[自研 NCC (FFT+积分图)] score=1.00000 @(132,288)  127.2 ms/次  ✓
[cv2.matchTemplate]    score=1.00000 @(132,288)   20.4 ms/次  ✓
```

**快 6 倍**，而且这就是自检里那条一直「跳过」的**对照实现** ——
两套完全独立的实现给出同一个位置，是匹配正确性最有力的证据
（此前 cv2 缺失，只能跑自研路径，无从对照）。

## 9. 修正后的架构：不再依赖「补锚点」

8.3 的否定结论让原计划（第 6 节：进游戏抄界碑补锚点）不可行。但**换个坐标基准**，
整件事反而变得更简单。

### 9.1 官方坐标系是每图本地画布 —— 再补一条硬证据

之前用「map0/map1 缩放比 1.5002」推断每图独立画布，那是间接证据。
现在有一条**不依赖任何游戏操作、纯靠接口数据**的判据：

**开封皇宫（map6）地理上位于开封（map1）城内。若官方经纬度是全局公共空间，
map6 的点必须落在 map1 的坐标范围内（子集关系）。实测：**

```
父 map1 开封       lng[-425207, 111546]  lat[-152525, 505770]
子 map6 开封皇宫    lng[-622055,-236126]  lat[ 131770, 722634]

子区域点在父区域经度范围外：189/355 = 53.2%
子区域点在父区域纬度范围外：152/355 = 42.8%
子包围盒是否被父包围盒包含：**否**
```

子区域的包围盒**不被父区域包含** → 官方坐标不可能是全局的 → **只能是每图本地画布**。

（对照：风催凉州 map3 恰好被河西 map2 包含，但那不构成反例 ——
包含可以碰巧成立，不包含则**证伪**全局性。）

### 9.2 新方案：以官方坐标系为准，两个基准并存

既然官方坐标是每图本地的，而我们的手工数据只覆盖清河 + 开封（正好对应 map0 + map1）：

| 数据 | 存放基准 | 说明 |
| --- | --- | --- |
| 官方 8192 点 | **官方各自图的本地图坐标系**（原样） | 一个字都不用换算，9 张图全覆盖 |
| 手工 6071 点 | 换算进 map0 / map1 的官方坐标系 | 用手上已有锚点解出的**逆变换**，误差 2.2%/2.1% |
| map2~8 | 官方数据直接用 | 手工数据本来在这几张图就是空的，**不需要任何锚点** |

**收益**：地图显示、检索、导出这些功能**一次都不需要进游戏**，
也不必去补那 7 张图的锚点 —— 原本卡住整个计划的依赖直接消失了。

**代价**：手工数据换算进官方坐标系会引入 2.2% 的误差。
但手工数据在 map0/map1 本来就有 2130+3941 个点，官方在这两图有 3323 个点，
两边的**重叠部分**（主要是 70 个界碑）可以互相校验；不重叠的部分各留各的。

### 9.3 那「识途自动寻路」怎么办？

自动寻路需要在**游戏地图上点一个位置**。游戏地图的像素 ↔ 世界坐标关系，
和官方坐标系无关，需要**单独标定**，但这跟官方接入是两件独立的事：

1. 打开游戏地图，用模板匹配找出若干**已知界碑**的图标像素位置；
2. 这些界碑的世界坐标我们**手上就有**（清河+开封的手工数据）；
3. 用 3 个以上对应点解出「地图像素 ↔ 世界坐标」的仿射关系（含缩放/平移）；
4. 之后任何世界坐标都能换算成地图上该点哪里，直接 `click_at`。

这条路**只需要在清河/开封标定一次**（因为游戏大地图是连续的，不像官方那样分 9 块），
标定完就能对全图任意位置下点。
